## Key concepts

### A stack is a convention, not a hardware primitive

"The stack" is just a region of memory with `sp` pointing at the top (lowest used address). Nothing prevents you from having multiple stack regions in memory — the CPU only tracks one `sp` at a time, so there is only one *active* stack, but others can sit in memory waiting. Per-task stacks are just this: each task owns a region, and switching tasks means pointing `sp` at the right one.

### A frame is any reserved region on the stack

C function frames (locals, return address) and the `boot.S` trap frame are the same thing mechanically: `sp -= N`, store stuff, use it, restore, `sp += N`. The difference is purpose, not mechanism. The compiler generates frame setup/teardown automatically; `boot.S` does it by hand. When the timer fires, `boot.S` allocates 248 bytes on the current stack and saves all 31 GPRs there — that's the trap frame. The `frame` pointer passed to `kernel_trap` is just `sp` after that allocation.

### The trap frame lands on the same stack as everything else

Confirmed experimentally: with `sp = 0x800018b0` in the spin loop, the trap frame landed at `0x800017b8` — exactly 248 bytes lower. Not a separate region; the same stack, just grown further downward by the trap entry code.

### Why shared stacks break context switching

If two tasks share one stack, task A's trap frame is saved somewhere on that stack. When task B runs, its function calls grow the stack downward too — potentially into task A's saved frame. There's no safe place to "reserve" space because the stack is dynamic. The fix is separate stack regions: task A owns one, task B owns another, neither can grow into the other.

### Stack overflow is a real gap, no protection yet

Without virtual memory and guard pages, nothing prevents a task from overflowing its stack into adjacent memory. For now the approach is "make stacks large enough" — a known limitation to revisit when paging is implemented.
