## New functions

### `print_char(char c)`
Isolates the UART write. All other print functions build on this. The hardware boundary lives here and nowhere else.

### `print_hex(unsigned int integer)`
Prints an unsigned integer as a hex string with a `0x` prefix. Delegates to `print_hex_recurse`.

### `print_hex_recurse(unsigned int integer)`
The recursive worker. Divides by 16, recurses on the quotient first (so digits come out most-significant first), then prints the remainder as a hex digit. Base case is `integer == 0` — just return, no output.

The split between `print_hex` and `print_hex_recurse` exists because the two jobs conflate badly in a single function:
- The wrapper owns: printing `0x`, handling the `0` edge case
- The recursive function owns: digit extraction, nothing else

Trying to do both in one function requires distinguishing "first call with 0" from "recursion bottomed out at 0" — same input, different meaning. The two-function structure eliminates that ambiguity.

## Key C / design concepts from this session

### ASCII arithmetic
Characters are just integers. `'0'` through `'9'` are consecutive in ASCII (48–57), as are `'a'` through `'f'` (97–102). So:
- digit 0–9: `digit + '0'` gives the right character
- digit 10–15: `digit - 10 + 'a'` gives the right character (equivalently `digit + 'W'` since `'W'` == 87 == `'a' - 10`, though this form requires a comment to be readable)

### Recursive digit extraction
Dividing by the base and taking the remainder naturally produces digits least-significant first. Recursing *before* printing reverses this, giving most-significant first — no buffer or explicit reversal needed.

### Wrapper + recursive helper pattern
When a recursive function needs setup logic (prefix, edge cases) that should only run once, split it: a public wrapper for the setup, a private recursive function for the work. Trying to track "am I the first call?" inside the recursive function leads to fragile shared state or confusing conditionals.

### Void vs int return on print functions
Returning an error code only makes sense if there's a real error condition to detect. Writing to a memory-mapped register with no status feedback gives nothing to check, so `void` is the honest signature. Revisit if status register polling is added later.
