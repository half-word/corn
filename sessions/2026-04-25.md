## Tools used

### `nm <elf>`
Lists symbols in an ELF file with their addresses and type codes. Useful type codes:
- `B` / `b` — BSS (or COMMON) symbol, global / local
- `D` / `d` — data segment, global / local
- `T` / `t` — text (code) segment, global / local
- `R` / `r` — read-only data, global / local

### `nm <object file>` vs `nm <elf>`
Running `nm` on the unlinked `.o` file shows what section the *compiler* emitted each symbol into (e.g. `.sbss`), before the linker resolves addresses. Running it on the final ELF shows resolved addresses but loses section name detail. When tracking down a misplaced symbol, check the object file first.

### `objdump -t <object file>`
Similar to `nm` but also shows section headers and their sizes. Useful for seeing all sections the compiler emitted, including empty ones (`.bss`, `.sbss`, `.data`, etc.).

## The .sbss discovery

Adding `int beef;` (uninitialized global) caused `beef` to land at `_stack_top` — the same address — rather than between `__bss_start` and `__bss_end`. The BSS zeroing loop still saw an empty range.

`nm kernel.o` revealed:
```
0000000000000000 g     O .sbss  0000000000000004 beef
```

The RISC-V toolchain emits small globals (by default, variables ≤ 8 bytes) into `.sbss` (small BSS) rather than `.bss`. The linker script only had `*(.bss .bss.*)`, so `.sbss` was orphaned and placed after all defined sections — landing at the same address as `_stack_top`.

Fix: add `*(.sbss .sbss.*)` to the `.bss` output section in `kernel.ld`, alongside the existing `*(.bss .bss.*)` and `*(COMMON)` lines.

## What lands in BSS vs other sections

| Declaration | Section |
|---|---|
| `int x;` (file scope, uninitialized) | `.bss` or `.sbss` depending on size |
| `int x = 0;` (file scope, zero-initialized) | `.bss` or `.sbss` |
| `int x = 5;` (file scope, non-zero) | `.data` |
| `const int x = 5;` (file scope) | `.rodata` |
| `int x;` (local variable) | stack — BSS never involved |

The BSS section exists so the binary doesn't have to store a large block of zeros. The kernel's `_start` fulfills the C standard's guarantee that zero-initialized globals are zero before `main` runs.

## Verifying the zeroing loop

Simply adding a zero-initialized variable isn't sufficient to verify the loop — writing zero to a location that's already zero is indistinguishable from not running at all.

The test: in `boot.S`, before the zeroing loop, write a non-zero value directly to `beef`'s address using `li` + `sw`. Then check in `kernel_main` whether `beef` is zero and print accordingly.

Confirmed:
- With `.sbss` in the linker script: loop ran, `beef` was zeroed
- Without `.sbss` in the linker script: `beef` retained the poisoned value, loop didn't cover it

## Hardcoded addresses are fragile

The test used `li t3, 0x80000088` (beef's address at the time). Adding instructions to `.text` in `boot.S` caused everything after `.text` to shift — `.rodata`, `.data`, `.bss` — so `0x80000088` no longer pointed at `beef`. The write corrupted something in the middle of another section, producing an `unimp` trap.

The right approach is to reference symbols by name in assembly (e.g. `la t3, beef`) so the assembler/linker resolves the address regardless of layout. Hardcoded addresses are only valid for things fixed by hardware (like the UART at `0x10000000`).
