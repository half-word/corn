# Session 2026-05-14

## What we did

- Defined `struct saved_registers` in `kernel.c` and changed `kernel_trap` to accept a pointer to it instead of a raw `uint64_t`
- Implemented the register restore path in `boot.S` after `call kernel_trap` returns: 30 `ld` instructions to reload all saved registers, `addi sp, sp, 248` to deallocate the frame, then `mret`
- Discovered the trap was looping (printing "Oh no!" repeatedly) because `mepc` wasn't being advanced — `mret` kept returning to the same faulting instruction
- Added `mepc` advancement before the restore: `csrr t0, mepc` / `addi t0, t0, 4` / `csrw mepc, t0`
- Traced with the debugger and found +4 was landing at invalid addresses, causing cascading traps
- Identified the root cause: the C extension was enabled (`misa` bit 2 = 1), so the compiler was generating 2-byte compressed instructions in places — +4 was skipping past instruction boundaries
- Decided to disable the C extension by changing `-march=rv64gc` to `-march=rv64g` in the build
- After that change: trap fires once, prints debug info, execution resumes normally

## Key concepts

### Struct as a typed view onto memory

The struct doesn't do anything at runtime — it just gives the C compiler (and the programmer) symbolic names for byte offsets that already exist in the frame. Field declaration order must match save order in the assembly exactly. `uint64_t` fields pack with no padding, so `offsetof(struct saved_registers, field)` should match the corresponding `sd` offset in the assembly.

### sp restore is implicit

`sp` is pre-saved in the frame at offset 8, but there's no explicit `ld sp, 8(sp)` in the restore path. It doesn't need one: `addi sp, sp, 248` always recovers the original `sp` value by arithmetic. Explicitly loading `sp` from the frame would also work, but it's redundant.

### The restore path belongs in assembly

`mret` is a privileged instruction C can't express, and restoring registers means clobbering the C runtime's own register state. The C handler returns normally via the calling convention; the assembly picks up after the `call` and does the restore.

### mepc and the two kinds of traps

For synchronous exceptions (faults): `mepc` points at the faulting instruction itself. To resume after it, you advance `mepc` before `mret`. The +4 here is a deliberate skip-and-continue, valid as a debugging scaffold but not generally correct behavior — a real kernel would panic on a kernel fault, or terminate the process on a user fault.

For interrupts: `mepc` already points at the instruction that was about to run when the interrupt arrived. It didn't fault — it just got interrupted. You don't advance `mepc`; you handle the interrupt and `mret` straight back.

### The C extension and instruction length

RISC-V base instructions are 4 bytes, but the C extension adds 16-bit compressed encodings. With the C extension active, the compiler may emit 2-byte instructions, and +4 can land in the middle of an instruction stream. The bottom 2 bits of the 16-bit instruction word encode the length: `11` means 32-bit, anything else means 16-bit. To handle this correctly in general you'd read the instruction at `mepc` and branch on those bits. The simpler fix for a learning kernel is to disable the C extension entirely (`-march=rv64g`), guaranteeing all instructions are 4 bytes.
