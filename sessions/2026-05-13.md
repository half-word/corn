## Key concepts

### Stack pointer convention

`sp` points to the lowest address byte of the last *used* element (full-descending stack). The first free byte is at `sp - 1`. To push an 8-byte value: decrement `sp` by 8 first, then store. Writing to `0(sp)` before decrementing would clobber existing stack data.

### Frame layout math

Allocating a frame with `addi sp, sp, -N` gives you valid slots at offsets `0(sp)` through `N-8(sp)` (in 8-byte steps). Offset `N(sp)` after the decrement is back at `original_sp` — which is occupied, not free.

A save done *before* the `addi` at address `original_sp - K` lands at offset `N - K` within the frame (relative to the new `sp = original_sp - N`). This is how the `sp` pre-save trick works: `sd sp, -16(sp)` before `addi sp, sp, -24` writes to `original_sp - 16`, which is offset 8 inside the 24-byte frame.

### The sp-saves-sp problem and the pre-save trick

`sp` needs to be in the frame, but building the frame modifies `sp`. The approach used here: save `sp` to its intended frame slot *before* the `addi`, using a negative offset from the current `sp`. You have to work out the right offset: `-(frame_size - intended_slot_offset)`. For a 24-byte frame with `sp` at offset 8: `-(24 - 8) = -16`, so `sd sp, -16(sp)`.

After `addi sp, sp, -24`, that pre-saved value is sitting at exactly offset 8 in the frame — no extra work needed.

### `sd` vs `mv`

`sd` stores a register's value to memory. To copy a register value to another register, use `mv` (or `addi rd, rs, 0` under the hood). `mv a0, sp` copies the frame base address into `a0` so it gets passed as the first argument to `kernel_trap`.

### Passing a pointer to C

The RISC-V calling convention puts the first function argument in `a0`. Setting `mv a0, sp` immediately before `call kernel_trap` passes the trap frame base address to the C handler. On the C side, the signature is `void kernel_trap(uint64_t sp)` — accepts the frame address as a raw integer for now.

## State of the code

`boot.S` trap handler:
- Pre-saves original `sp` at `-16(sp)` before frame allocation
- Allocates 24 bytes (`addi sp, sp, -24`)
- Saves `ra` at `0(sp)`, `gp` at `16(sp)` (original `sp` is at `8(sp)` from the pre-save)
- Sets `a0 = sp` (frame base pointer) then calls `kernel_trap`

`kernel_trap` in `kernel.c` accepts the frame pointer, prints it as hex, then continues printing `mcause`, `mepc`, `mtval` as before. Halts at the end.

The wiring is solid. This is still a partial frame — only ra, sp, gp are saved, and several registers (all caller-saved ones) are clobbered by the `call kernel_trap` instruction before the C handler runs.

## Next session

The natural next step is extending the frame to all 31 general-purpose registers. A few things to think about before starting:

- Order and `call` clobbering: `call kernel_trap` overwrites `ra` and all caller-saved registers (`a0`–`a7`, `t0`–`t6`). These must be saved before the `call`, or their pre-trap values are lost.
- The `a0` slot is tricky: `mv a0, sp` overwrites `a0` before the call. So `a0`'s pre-trap value needs to be saved before that instruction.
- Once the full frame is in place, the C side can be updated to accept a proper struct pointer instead of a raw `uint64_t`, and can read individual register values by field.
